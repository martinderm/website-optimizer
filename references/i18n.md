# Internationalisation and hreflang

A site in more than one language, or the same language for more than one region,
tells a search engine which version belongs to whom. `hreflang` is how it says so.

This is not about translating a page. It is about two pages that are the same
thing in two languages, and about which one a searcher in Vienna and a searcher in
São Paulo should each be shown.

## What the signal is

```html
<link rel="alternate" hreflang="de-AT" href="https://example.at/leistungen/">
<link rel="alternate" hreflang="de-DE" href="https://example.de/leistungen/">
<link rel="alternate" hreflang="x-default" href="https://example.com/services/">
```

- The value is a **language** code from ISO 639-1, optionally followed by `-` and
  a **region** code from ISO 3166-1 alpha-2: `de`, `de-AT`, `pt-BR`, `en-GB`.
- **Those two lists are the whole supported set.** Google states that codes
  outside them are not supported and names `es-419` as an example. This matters
  because `hreflang` *looks* like BCP 47 and is not: BCP 47 permits values
  (language-region groupings, three-letter languages, private subtags) that a
  search engine ignores. A validator that checks BCP 47 will pass things that do
  nothing.
- A script subtag from ISO 15924 is accepted where a script matters: `zh-Hant`,
  `zh-Hans`, optionally with a region (`zh-Hans-US`).
- **The language comes first and cannot be omitted.** `be` is not Belgian; it is
  Belarusian. `EU`, `UN` and `UK` are reserved for something else and have no
  effect. Region-only values are invalid.
- Value case does not matter to Google, but the alpha-2 convention is uppercase,
  and writing `en-GB` keeps a human reader right about which half is which.
- `x-default` names the page for a searcher whose language matched nothing. It
  takes no language code, is optional, and is designed for a selector or an
  auto-redirecting home page. On a site whose pages are all one language it is the
  only line that does anything.
- **Alternate URLs must be fully qualified**, transport included:
  `https://example.com/foo`, never `//example.com/foo` and never `/foo`.

## The reciprocal rule

If Vienna points at São Paulo, São Paulo must point at Vienna. Google's words:
*"If two pages don't both point to each other, the tags will be ignored"* — the
reason given is sound, that anyone could otherwise declare their page an alternate
of yours.

A one-way link therefore fails and the failure is invisible on the page that has
it, because that page's own markup is correct.

**Completeness is the guideline; reciprocity is what is enforced.** Google's
guideline is that each version lists itself *and* every other version, and its
troubleshooting section then allows an incomplete set — *"you can omit some
languages on some pages; Google will still process the ones that point to each
other"* — while insisting that a newly added language links bidirectionally to the
site's dominant one. So: pair-by-pair correctness is the hard requirement, a
complete matrix is the goal.

This is the part no single page can be checked for. It is a property of the set,
and it is the same graph shape `links` had to build.

## Where the annotation may live

Three methods: the `<link>` elements above, an HTTP `Link:` response header (the
only one that works for a non-HTML file such as a PDF), and `<xhtml:link>` entries
inside a sitemap.

Google treats the three as equivalent, and says using all three at once brings no
benefit — only three implementations to keep in step. **Pick one.** The sitemap
form is the one to reach for where the HTML is produced by something you do not
control; the head form is the one to reach for everywhere else.

## What goes wrong

- **Missing return link.** The commonest failure, and the one nobody sees.
- **No self-reference.** The page's own annotation is missing, so it is absent
  from the set it belongs to.
- **A code outside the two lists.** `en-UK`, `es-419`, region-only values.
  Ignored, silently.
- **`x-default` carrying a language code**, or pointing at a language page rather
  than at the neutral one.
- **Relative or protocol-relative `href`.** Both are explicitly rejected.
- **`hreflang` on a `noindex` page.** The page asks not to be indexed while also
  asking to be chosen for a language.
- **The variants are not variants.** Pages are only duplicates in Google's sense
  if the *main content* is untranslated. Two pages differing in a currency symbol
  are one page with a setting; `hreflang` does not fix that, it just gives both a
  language.

**What is *not* on this list: the `<html lang>` attribute.** Google states plainly
that it uses neither `hreflang` nor `lang` to detect a page's language. A
contradiction between them is therefore not a search defect — but `lang` is what a
screen reader uses to choose a voice, so a page declaring `lang="de"` while
serving English is an accessibility defect (`accessibility.md`). Worth saying
because the two are usually described together and the reason differs.

## Canonical and hreflang together

*Practice, not specification (`partially_supported`).* A language page should name
itself as its own canonical. A canonical pointing at the *other* language's version
tells the engine that only one of the two deserves to rank, which is the opposite
of what the `hreflang` set above it asks for. Google's localised-versions page does
not state this as a rule; it is the reading the practitioner community settled on,
and it is consistent with the two signals meaning what they mean.

## What a build audit can prove, and what it cannot

Worth separating before anyone promises a check.

**Checkable from build output**, because it is a property of the whole set:
- every pair is reciprocal, and every page is in its own set (**the item that
  matters most**)
- every `hreflang` value is a language from ISO 639-1, optionally with a region
  from ISO 3166-1 alpha-2 — and not merely well-formed BCP 47
- `x-default` appears exactly once per set, without a language code
- alternate URLs are fully qualified and absolute
- no page in a set is `noindex`
- one annotation method across the site, not three

**Not checkable from a build:**
- whether the *choice* of languages and regions is right, which is a business
  decision
- whether the variants really are variants — that is a judgement about content
- whether a search engine serves the intended version, which is visible in Search
  Console's international targeting report or by searching from that region
- the `Link:` header form, which is a response-header fact and needs a fetch

**And there is no capability yet.** Everything in the first list needs the whole
set, which is the same graph `links` builds; it has not been built because no bound
site has more than one language yet, and a checker written against imagined markup
would encode the imagination (D47). It becomes worth writing the moment a real
multilingual site is bound, and not before.

## Checklist

- [ ] Every page of a set lists itself and the other variants
- [ ] Return links complete in both directions, pair by pair
- [ ] Language code from ISO 639-1, region from ISO 3166-1 alpha-2
- [ ] No region-only values, no `en-UK`, no `es-419`
- [ ] `x-default` present once per set, without a language code
- [ ] Alternate URLs fully qualified with `https://`
- [ ] No `noindex` on any page in a set
- [ ] One annotation method, site-wide
- [ ] Canonical self-referential on each language page
- [ ] `<html lang>` agrees with the page's content (accessibility, not SEO)
- [ ] Search Console international targeting checked after launch
